# ADR 002 — Authoritative private shared state

Date: October 5, 2026. Status: provisional implementation; current-server hosted simulator checks verified October 20. PR readiness is tracked on PR #2; operational and physical-device limits remain below.

## Context

Milestone 2 needs two authenticated identities to share one private space. A role picker cannot authorize a user. Concurrent clients must preserve routine snapshots, fixed run roles, exact evidence versions and terminal closure. Account changes must clear protected state before delayed network responses can publish.

## Decision

Use Supabase Auth/Postgres through a Swift/Vapor command service that imports `SecondLookCore`. Compare the alternatives in [Backend Comparison](../Backend-Comparison.md). Pin Vapor 4.122.2 and Supabase CLI 2.119.0; keep the core package dependency-free.

The server verifies the bearer token with Auth on each request, then checks a configured allowlist of exactly two distinct account IDs. One account creates the singleton private space; the other joins through a random, targeted, expiring, one-use invitation. The database stores its SHA256 digest, not its plaintext. An unjoined owner can reissue an invitation without losing state by supplying its observed space revision. The database checks that revision under the lock and advances it on rotation, so concurrent same-revision calls cannot both succeed. The compatibility RPC permits initial creation only. Publishing a newer native revision clears older invitation metadata. The append-only October 12 migration is tested locally and installed in the existing hosted project on October 20 under explicit operator authorization, with exact stored-row preservation verified. A 15-minute invitation expiry is an engineering default; it is unrelated to reminders, photo retention or unreviewed timeout.

The phone sends typed commands with expected space/run/routine/evidence versions, never an actor, server clock or arbitrary replacement state. Explicit-space reads, command receipts and commits, and Debug evidence metadata validate that every returned snapshot has the requested space ID; unscoped discovery and pairing retain their separate discovery semantics. The service derives the actor from verified identity and applies the existing rules. Only privileged database RPCs can commit the resulting aggregate. A row lock and revision compare-and-swap atomically save state and an actor/request-bound command receipt. An identical retry returns current state plus the original created ID; reusing an ID with another actor or payload is rejected. A concurrent conflicting change requires a fresh snapshot and explicit new action.

Each new user action receives a fresh command ID, even when its body equals an earlier unresolved action. Only an explicit retry with the same ID may reuse the original envelope, including its expected revision. The phone retains unresolved ID/body pairs in session memory and exposes a specific retry control; it never infers retry intent from command equality. A server-confirmed command retains a separate memory-only receipt keyed to its exact backend/account/space, command ID and body, committed revision, and optional created ID. The coordinator may return that original result on explicit retry without another HTTP write, but only a verified active same-scope snapshot at or above the committed revision permits one-shot receipt consumption. Duplicate or staggered identical replies cannot revive an acknowledged receipt; in-flight tracking remains current-generation and scope-bound. A retry may return a newer current snapshot revision with the same committed created ID, so receipt matching preserves command identity without requiring the later snapshot revision to equal the first reply. Creation result IDs must be nonnil and match the actor/source of the returned run, or the immediate save-as routine; later exact save-as replay can remain valid after routine deletion. Noncreation IDs must be nil, and invalid replies remain unresolved. Created-ID guards and connected receipt/lifecycle probes pass against current source; Verification records focused regressions and the complete 123-case Core/transport package. The highest verified revision survives same-scope background/rebind independently of receipt consumption, preventing a lagging fetch from rolling back a known command. A live creation flow receives its successful original/retry receipt once through an exact-command/view-owner/presentation-epoch completion under the current foreground response epoch. Its fresh creation control stays disabled while that action is unresolved and offers explicit retry; abandoned/separate flows remain fresh intents. The adopted presentation policy for the same account and space keeps private connected editor inputs, checklist preferences, review notes, protected navigation and exact creation owners/callbacks in process memory across same-backend/account/space foreground revalidation. Backgrounding still advances the separate asynchronous response generation immediately and clears public snapshot/retry metadata. Frozen presentation cannot render, enter accessibility, or accept hits while access is unverified. Shared error alerts, which render outside that gate, are hidden on suspension and privately restored only after same-scope membership/fresh-revision verification, the original sheet lifetime and exact retry eligibility; losing scope or replacing the sheet discards them. Only genuine same-scope membership and a fresh coordinator fetch at least as new as the held revision may reveal it. A callback keyed by command ID, view owner and presentation epoch may complete only under the current foreground response epoch; a stale response cannot consume a resumed receipt. Explicit abandonment, access loss, sign-out, configuration/account/space change or genuine not-paired/scope-mismatch state clears presentation, drafts and callbacks. A command-level membership/scope loss invalidates both coordinator and model generations immediately, purges issued actions and in-flight acknowledgements with retained receipts/revision floor, and keeps the verified Auth vault only for a new genuine membership lookup. A stale admitted reply cannot republish after that invalidation. Process termination preserves none of this and there is no durable draft or offline queue. This revision is a reversible implementation choice with current-source local native acceptance recorded October 16. Loaded local and connected state must correlate every closed run with its text archive, including fixed participants, ordered item history and decisions attributed to that run's reviewer. Connected item versions must remain below `Int.max` before increment-capable commands may touch them. All-standard closure needs no evidence cleanup; completed high-priority evidence cannot claim cleanup was unnecessary. Connected legacy test evidence must use the exact `M2-SYNTHETIC-NO-REAL-PHOTO` fixture ID and `simulatedCamera` source; arbitrary local demonstration fixture IDs stay local.

The private SQL schema is not exposed to PostgREST. Its tables have no direct client privileges and RLS is enabled. Public definer RPCs have a fixed empty search path and grant execution only to the service role. This credential is a trusted server capability, not client authorization; it never belongs in app configuration.

Connected iPhone state is memory-only in M2. Keychain holds account credentials scoped to app identity and provider/server configuration. Response generation gates network publication, errors and credential writes; presentation generation separately identifies a still-owned private view/draft through a same-scope suspension. Foreground polling/manual refresh fetch server snapshots; commands publish only after successful server commit, and frozen presentation needs the additional membership/revision-floor check above. Local M1 stores and Debug role/fixture controls are a separate composition.

Saved-session restoration admits one operation before reading or binding credentials. Invitation renewal clears the old displayed code before sending the request, because a committed rotation can invalidate that code even if its response is lost. Initial creation and joining invalidate confirmed absence before sending; an uncertain or rejected result requires a genuine membership lookup before another pairing mutation. Account and foreground invalidation still prevent older responses from publishing. Debug localhost acceptance may deliberately discard a genuine pairing response or enqueue concurrent restores; those triggers are explicitly labeled simulated and are excluded from Release.

## Boundaries and consequences

The JSONB aggregate deliberately favors one bounded private space over premature entity infrastructure. It requires aggregate size and performance review before broadening scope. The Swift service introduces hosting, availability, TLS, rate-limit, monitoring and secret-rotation responsibilities. No production deployment is implied by a local development configuration.

M2 has no real photo send API. A Debug server on explicit loopback local-development configuration may create clearly synthetic evidence metadata solely for review authorization tests. Normal composition and Release reject this capability. M3 still owns photos, object storage, media authorization and real cleanup. Unpairing, remote jobs, push and distribution remain deferred.

Local Auth/Postgres/HTTP tests establish local behavior only. The Free follow-up below records hosted provisioning and public boundary checks; hosted pairing, standard commands/receipts/versions/concurrency/snapshots/closure, refresh, relaunch/foreground on both existing clients, sign-out/outsider denial, restart and observed Free idle/wake recovery are verified. PR review/CI readiness, region/privacy review, operational backup/incident checks and physical-device acceptance remain distinct from these runtime results. Do not declare the full M2 exit complete from unit tests, localhost evidence or public health/denial probes alone. Operations and test commands are in [Backend Operations](../Backend-Operations.md); actual evidence belongs in [Verification](../Verification.md).
