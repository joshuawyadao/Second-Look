# Architecture

## Local foundation boundary

Milestone 1 established a native, local iPhone app. The checked-in `SecondLook.xcodeproj` builds SwiftUI views in `SecondLook/`; a dependency-free `SecondLookCore` Swift package owns checklist rules and local persistence. This reversible foundation permits simulator builds and portable rule tests, with iOS 17 as the provisional deployment floor. Its Debug `SECONDLOOK_DEMO` composition exposes synthetic role/evidence/retry/cleanup controls and uses a separate demo data location. Release excludes those controls. [ADR 001](decisions/001-native-local-foundation.md) records the foundation choice. Build and test outcomes belong in [Verification.md](Verification.md).

| Milestone 1 layer | Owns | Does not claim |
| --- | --- | --- |
| Core models and transitions | Routine definitions, run snapshots, fixed actor/version checks, progress, simulated submissions/decisions, terminal state, text-only archive, independent settings | Server authorization or physical proof |
| Local store | Versioned JSON in Application Support, atomic writes, explicit decode/write errors, restoration of definitions/runs | Shared sync, backup/retention guarantees, real media storage |
| SwiftUI app | Routines, Review, History, editor/checklist/preview/settings navigation; accessible labels and honest local/simulated status | Authenticated identities, capture, remote sending, push |
| Debug demo adapter | Synthetic participant/evidence responses and failure/retry/cleanup-pending paths, isolated from personal data | Real upload, another-device review, deletion |

Pass time explicitly to core commands and use fixed timestamps in tests; no expiry scheduler runs yet. Commands should change state only after actor, item, run, and expected submission-version checks. Persist the result before presenting it as durable; a save error must remain visible and recoverable. A local draft must never be labeled sent.

Restoration correlates each text-only archive with its closed run: fixed participants, title/routine/start, ordered item text/priority/check times and prior decisions must match. Any retained final decision uses the last submission version and the assigned reviewer; a completed high-priority item requires its final approval. Both local loading and connected snapshot validation use this rule. Archive items store neither item IDs nor a separate review-status field; the validator does not invent absent metadata.

## Key records and invariants

Withdrawal takes an expected submission version through the core and native confirmation path. It rejects an old intent before mutation and retains a separately prepared replacement draft. Relaunch preserves that draft, and sending it advances the submission version rather than reusing the withdrawn version.

Restoration binds each current decision to the assigned reviewer and exact current submission version. Approved/requested status must match its verdict; a request needs a nonempty note. Only accepted evidence can carry a decision, while sending/failed/waiting records carry none. Draft previews stay separate and use the next version. Inconsistent records fail loading as a corrupt document before becoming editable state; loading does not silently repair or overwrite the saved file. This strengthens schema-v1 validation without a schema migration or connected authorization claim.

`Routine` and ordered `RoutineItem` are mutable definitions. `ChecklistRun` and `RunItem` snapshot requirements, participant roles, and settings at start; a one-off run has no routine ID. `PhotoSubmission` carries one current item/version/source/status and an optional accepted-at time; review deadlines are deferred; `ReviewDecision` names exact version, actor, decision, note, and time. A run closes as Completed only if all standard items are checked and all high-priority current submissions are approved. Canceled is separate and terminal. Only the assigned other participant may review. Committing replacement/withdrawal invalidates approval; discarding a preview does not. Closed runs reject later changes. Archive output contains text only.

`ReminderPreferences` and review-timeout settings are separate models; timeout starts Off and no M1 scheduler runs. M1 stores one run-level snooze/mute/quiet-hours set; recipient-specific controls and timezone-aware scheduling still need modeling before Milestone 5. `CleanupStatus` is separate from run outcome: not needed without evidence, pending for synthetic evidence at closure, or a simulated acknowledgment. Durable `CleanupWork` jobs remain later work. Pending or failed cleanup cannot be displayed as confirmed deletion. The local adapter models transitions without real image bytes. No app-managed image or live URL belongs in the archive.

The shared native preference fields initialize an enabled snooze one hour ahead, constrain new selections to the future, and show an expired saved value without renewing it. This editable example is saved with the routine/run settings; it does not create a reminder scheduler or an agreed cadence.

Completed text archives require a check timestamp for every standard item; high-priority items never have that standard-check field. Every non-nil reviewer differs from the performer, including standard-only runs. A canceled history must remain unsatisfied when final approvals are reconstructed from its matching archive; prior withdrawn approvals do not satisfy the closed item. Completed high-priority histories require pending or simulated-confirmed cleanup because their submissions existed at closure. Canceled unsubmitted evidence may legitimately need no cleanup. A final archive decision beyond the run item's retained prior decisions proves current evidence existed at closure, including canceled runs; its cleanup cannot be not needed. A withdrawn prior decision alone does not prove evidence remained at closure. The shared loading validator enforces these rules even if run and archive contain matching corrupt values.

Prior review decisions must use the assigned reviewer, positive increasing versions within the item history and domain verdict/note semantics. Current and archived decisions reuse the same semantic helper. A removed current submission may leave its reviewed version equal to lastVersion in canceled history; an existing submission must follow prior versions.

A run stores either no routine source ID/version for a one-off, or a routine ID with a positive immutable source version. Creation and local/connected loading share this rule. Deleting or editing the live source routine does not invalidate the run snapshot.

## Native privacy cover

Each scene owns an opaque privacy window above its presented sheets and alerts. Scene/app deactivation shows the cover; activation removes it. The cover does not become the key window or replace editor state. Scene attachment and disconnection manage its lifetime independently of sheet navigation. This protects local checklist content as well as future media; it is not an access-control mechanism.

Only `SECONDLOOK_DEMO` launches with both `-ui-testing` and `-privacy-testing` register show/hide Darwin notification hooks for deterministic UI tests. These test signals invoke the same cover controller as scene activation; observers are removed on disconnection. Release compilation excludes the hooks, and the built-binary boundary check rejects their markers. Tests cover the root screen, routine editor, and Local settings sheet. OS snapshot timing and keyboard behavior still require device/runtime acceptance; observed simulator evidence is in [Verification.md](Verification.md).

## Milestone 2 connected boundary, in progress

The [backend comparison](Backend-Comparison.md) and [ADR 002](decisions/002-private-shared-state.md) record a reversible choice: Supabase Auth/Postgres behind a Swift/Vapor command server. The service reuses the dependency-free core transitions rather than trusting client mutations. It validates each bearer token with Supabase Auth `getUser`, derives the actor, checks the explicit two-account allowlist and current space membership, and supplies server time. Password sign-in and refresh occur through Auth; the iPhone receives only public configuration and keeps session credentials in Keychain.

The private Postgres schema holds one shared space with at most two distinct account IDs, its core state, a monotonic revision, a targeted expiring invitation hash, and command receipts. Only server-side service-role RPCs can create/join/read/commit; direct app roles have no table or RPC access. Every connected command first derives the actor from verified Auth, checks the configured two-account allowlist and current membership, then applies domain policy. The owner can rotate an unused invitation without resetting state only when its observed revision matches the locked row; rotation advances that revision. Concurrent calls at one revision cannot both replace the token. The older RPC signature permits initial creation only, and newer native snapshots clear older displayed invitation metadata. Joining consumes it under a row lock. Each command checks the expected shared revision and relevant core versions, then atomically writes the new state, revision, and actor/request-bound receipt. Repeated command IDs with a different actor or body fail; an exact retry returns the current snapshot and original created ID. Loading rejects an open run whose items are all satisfied, because valid transitions close it atomically. Run snapshots fix performer/reviewer roles; an owner cannot review their own high-priority item, and a terminal run cannot reopen. Closed all-standard runs need no evidence cleanup; completed high-priority runs with accepted synthetic evidence cannot claim no cleanup is needed. Connected snapshots reject `.simulatedConfirmed` cleanup acknowledgment because no authenticated connected command can produce it; local demo persistence retains that explicitly simulated transition. Release snapshot validation rejects every current connected submission until a real media path is implemented, even if it carries the synthetic fixture marker. Debug snapshots admit synthetic metadata only with fixture ID `M2-SYNTHETIC-NO-REAL-PHOTO` and source `simulatedCamera`; arbitrary local M1 fixture IDs remain local demonstration data. This compile-time boundary does not change local demo persistence or closed text-only archives after references are stripped. Explicit-space reads, commands and the Debug synthetic-evidence route reject a provider/receipt/commit snapshot from any space other than the requested ID, even if its other fields are valid; only unscoped discovery and pairing may return a newly discovered space. Connected snapshots reject an item version at `Int.max` before a future increment could overflow. An open run also reserves two revision increments for an item edit followed by automatic closure, keeping `Int.max` unused in the resulting snapshot; terminal history may retain `Int.max - 1`. The command interface does not accept arbitrary client state.

Closed runs retain a text-only `hadEvidenceAtClosure` fact, computed before current synthetic references are stripped. Open runs require no marker; closed runs require a Boolean. False requires Cleanup not needed; true requires pending cleanup or the local-only simulated acknowledgment. This also covers canceled undecided previews and submissions, whose archive has no final decision. State encoding writes `closureProvenanceVersion: 1`; versioned documents cannot omit a closed marker. Unversioned documents are legacy only when every run omits the new key, including explicit null. Legacy closed markers are inferred in memory from matching run/archive cleanup statuses, validated normally, and normalized on the next ordinary save or revisioned command. Loading does not rewrite bytes. The outer local document, shared envelope and SQL RPC versions stay unchanged; connected JSONB is opaque, so this requires no SQL migration. Already discarded legacy undecided evidence cannot be reconstructed, and unsigned wholesale conversion back to legacy shape cannot be authenticated; the server remains the sole connected-state writer.

The core coordinator retains the original command ID, body, space and expected revision when a reply is ambiguous. A fresh action always receives a fresh command ID, even when its body equals an earlier action. Only an explicit retry ID reuses the original envelope after a newer snapshot arrives. A confirmed command has a separate, session-memory receipt bound to its exact backend/account/space, command ID and body, committed server revision, and optional created ID. An explicit retry of that confirmed ID returns the original result without another HTTP command and does not consume the receipt. Only a verified active same-scope snapshot at or above its committed revision permits one-shot consumption by the original presentation. The model also retains its first authenticated unscoped membership revision as a publication floor: a lagging initial explicit-space fetch cannot replace that newer view or authorize a command at the older revision. Refresh supplies the authenticated membership and visible/held verified snapshots to the coordinator. Before it publishes a fetched view, it validates every reference for the exact account/space, rejects disagreement at the same revision, and requires the fetched revision floor and full equality at equal revisions. First-command preflight also supplies its visible reference. Rejection leaves coordinator snapshots, pending envelopes and confirmed receipts unchanged, so a malformed response cannot poison recovery or escape through receipt consumption. If a rejected initial command preflight leaves the coordinator empty, the model retains its already verified view; only an admitted candidate may replace it. Known access/scope loss clears before that error handoff. Increasing revisions must also preserve ordered membership: only the same array or a one-owner to owner-first two-member append is valid in M2. Trusted-reference chronology, fetched views and command publication reject peer removal/replacement and owner reordering; unpairing/ownership transfer remain unimplemented. Increasing revisions also retain every known run/archive ID and preserve closed runs and their text archives exactly. The guard covers chronological trusted references, reference-to-fetch comparison and seeded command/refresh publication; open progress/closure, new runs and routine deletion remain valid. Overlapping or delayed identical responses cannot re-create an acknowledged receipt; in-flight tracking is bound to the current generation and scope. The coordinator retains the highest verified revision independently of receipt consumption across same-scope background/rebind, so a lagging fetch cannot roll back a previously accepted command. Duplicate receipts may carry a newer current snapshot revision while retaining the same committed created ID; the original action identity, rather than equality of later snapshot revisions, determines whether they match. Creation responses require a nonnil created ID that was absent from the objects known when the exact action was first sent. This original object-ID set stays with an unresolved envelope through refresh and retry, so a genuine committed creation remains recoverable while an older object cannot be substituted: run-start/repeat IDs must name a returned run owned by the active performer with the matching source-routine semantics, and a repeat is a distinct run. Save-as needs a routine ID in the immediate commit view but permits a later exact receipt replay after that routine was deleted. The original ID in that later replay is authoritative receipt data from the authenticated service/private SQL, not a caller-selected claim. SQL binds the stored ID to space, command ID, actor and request digest and ignores a replacement created-ID argument on duplicate commit. The HTTP envelope rejects extra result-ID fields. A current snapshot cannot prove the existence of a now-deleted routine; accepting that authoritative receipt preserves recovery. Self-consistent output fabricated by an adapter that violates this receipt contract is outside that authority boundary; a redundant witness from the same source adds no independent authentication. Noncreation responses must carry no created ID; malformed replies remain unresolved rather than publishing. Created-ID, transport and native recovery validation are recorded separately in [Verification](Verification.md). Access loss, genuine not-paired or scope-mismatch state, sign-out, account/backend/space change and end-session invalidate the coordinator generation and purge receipts, in-flight acknowledgements and the revision floor, so an already-admitted late reply cannot republish protected state. The native model retains each issued action's ID/body and offers Retry this action in its error alert plus a Retry unconfirmed action menu; ordinary taps create new intent. The native routine editor separately retains its definition's creation ID. The adopted presentation policy for the same account and space extends this private, process-memory suspension to connected editor inputs, checklist preferences, review notes, protected navigation, and exact live creation owners/callbacks for the same backend/account/space. A background transition immediately changes the asynchronous response generation and clears the public snapshot/retry metadata; retained presentation data remains frozen behind gates that hide it from rendering and interaction, with SwiftUI accessibility hiding applied. Foreground return must verify same-scope membership and obtain a fresh coordinator snapshot at least as new as the held revision before making presentation or retry controls visible. Only the exact command ID/view owner/presentation epoch callback under the current foreground response epoch can complete the original flow; an old-generation response cannot consume a resumed receipt. Access loss, sign-out, configuration/account/space change, or a genuine not-paired/scope-mismatch result clears the held presentation, drafts and callbacks. A command-level membership/scope loss takes this purge path immediately, retaining the verified Auth vault but requiring a new genuine membership lookup before pairing controls or private content return. Process termination clears everything; there is no durable draft or offline queue. Focused editor/settings/review, access-loss, receipt, scope-loss and alert native checks are recorded in Verification with their source and hosting limits.

Invitation renewal in the same backend/account/space refreshes the existing coordinator, preserving original unresolved command envelopes and explicit retry IDs. Async publication checks its session epoch and highest verified revision; caller mutations recheck the epoch. Only a matching published snapshot displays the renewed invitation. A real scope change clears pending memory.

The native form permits Create/Join only after a successful lookup confirms no space, or permits owner invitation renewal from a verified one-member snapshot. A failed lookup leaves pairing mutations disabled and offers a manual retry. Beginning renewal clears any displayed invitation before awaiting the server, since rotation can commit even if the response is lost; only a confirmed new result supplies a shareable replacement. All native Auth/command base URLs use one validation contract before storage and before HTTP: a nonempty host, HTTPS except explicitly allowed loopback HTTP, no credentials/query/fragment, and no non-root path. Server configuration rejects malformed/empty allowlist fields, hostless provider URLs and control characters in either provider header key. Recognizable modern prefixes and bounded decoded legacy role claims reject keys assigned to the wrong configuration slot. Decoded claims are only a format check; they never authenticate a key or actor. Malformed client bodies return bounded HTTP400; invalid provider or stored responses return bounded HTTP503.

Only a command-service response explicitly coded notPaired establishes absent membership. Auth user/refresh404 and uncoded or unknown command404 are service unavailability; they preserve unconfirmed membership and cannot enable pairing as if absence were verified. Command-service401/403 require their documented `unauthenticated`/`forbidden` codes before clearing an account and its credentials; uncoded, malformed or unknown responses remain service unavailability. Command-service409 likewise recognizes only `staleState` and `pairingUnavailable`, so an uncoded/unknown conflict cannot be mistaken for a definite revision rejection. Supabase Auth denial retains its separate provider semantics.

A retained run revision never decreases. An unchanged run revision requires the entire run to remain equal; changes require a higher run revision even when the shared-space revision advances.

Every retained run preserves its original performer and reviewer across newer shared revisions, including the transition to closure; structural membership alone cannot authorize a role reassignment. Its frozen title, template ID/version, start date and ordered item identity/title/priority/instructions also remain exact. Settings, checks, evidence, decisions and closure fields may legitimately progress while an earlier run is open. Editing/deleting templates or creating independent new runs does not rewrite a retained run definition.

For invitation renewal at expected revision N, the server captures a validated current snapshot and publishes a token only when the authoritative create result retains that owner-only space, ordered members and aggregate at exactly N+1. Exhausted revisions fail before addition. Initial creation needs no prior snapshot and publishes a token only for revision0, ordered members[actor] and the exact empty initial aggregate; SQL remains authoritative for stale revisions, ineligible callers and concurrent renewal/join outcomes. Malformed successful replies receive bounded503/no-store without a token.

A successful join additionally requires both distinct allowlisted accounts in its validated result; a caller-only reply receives bounded503/no-store rather than publishing a paired state. This does not constrain the actor to one member index, preserving idempotent SQL joins.

Starting a join marks membership unresolved and enables the active-scene recovery lookup before awaiting its response. Any non-access-loss failure, including a definite invalid invitation, requires an actual lookup before another pairing mutation: the error alone cannot prove the account still has no membership. A joined result publishes the space; a genuine not-paired result re-enables pairing and stops recovery polling. Authentication/membership loss still clears the protected session.

The native connected composition keeps shared state in memory and refreshes it after sign-in, foreground return, committed commands, manual refresh, and a five-second active-scene poll. Under the presentation policy for the same account and space, response generation changes immediately on backgrounding and protected public state disappears; a separate presentation generation may retain frozen same-scope drafts/navigation until the membership and revision-floor gates pass. Account-scoped response epochs reject stale network completions. Access loss, sign-out and scope change clear protected presentation as well as state. Debug XCTest launches may pass `-shared-no-periodic-poll` with both `-ui-testing` and `-shared-testing` to remove timer interference from a bounded acceptance scenario. This does not disable foreground lifecycle revalidation or manual refresh, and ordinary Debug/Release launches keep polling. The local Debug demo remains separate; its role picker is never authorization. The Debug localhost-only synthetic-evidence route supplies test metadata without an image. It rejects an exhausted space revision before mutation or addition with bounded503/no-store and no commit; the last available revision can still advance once. The production connected path has no real photo upload or synthetic-evidence command.

Sign-out clears memory and the active credential-writer binding immediately, then records a public configuration/app-namespace scoped restoration barrier before deleting Keychain credentials. Deletion accepts success or item-not-found; other statuses produce a bounded cleanup error. While the barrier exists, restoration retries only deletion and never reads/authenticates the leftover account. A successful fresh, verified credential write removes the barrier; a failed write or stale session cannot remove it. Keychain writes update the item or add it when absent rather than ignoring a preliminary deletion. Preferences contain the barrier and public configuration, never tokens. Recognized modern secrets and legacy service-role JWTs are rejected before configuration storage and Auth HTTP. A malformed Auth200 user body is a provider failure, so it does not masquerade as forbidden access and erase an allowed session.

Saved-session restoration rejects a busy operation before reading or binding a candidate. Since the model runs on the main actor and marks itself busy before its first suspension, concurrent lifecycle/reconnect entry points cannot bind competing vault sessions. Foreground/account epochs still reject stale completions, and Keychain writer IDs remain independently checked.

A refreshed Auth identity must match the installed vault account before credentials are stored. A mismatch invalidates the vault and follows the unauthenticated clearing path, including protected state and checked Keychain cleanup. A completion from an already invalidated session clears its refresh task and remains rejected by the session epoch.

Public refresh refuses entry while busy, and manual Refresh controls disable for the owning operation. Foreground revalidation and command recovery use a private refresh continuation; at most one refresh runs per session epoch, and an old completion cannot clear a newer epoch's refresh guard. Native mutation controls disable while synchronization is busy, including editor/settings saves, starting/repeating, deletion, withdrawal and review decisions. Switching to local lists is also disabled while busy, and the main-actor transition independently refuses entry before clearing session state or dismissing Account settings; normal switching resumes when synchronization finishes. This preserves an in-flight credential refresh owner. Draft inputs remain editable. An invocation racing refresh receives a bounded synchronization message rather than silently returning success or disappearing. Explicit unconfirmed-action IDs and their retry controls remain separate from a refused new invocation.

Shared error alerts are owned by the active presented sheet, using opaque lifetime IDs to suppress a competing root alert; the root presents errors when no sheet owns them. An alert lies outside the protected-content gate, so foreground suspension hides its message and retry immediately. Its private in-memory copy can return only after genuine same-scope membership, a fresh snapshot at least at the held revision, the same sheet lifetime and a still-valid exact retry ID; scope/access loss or a replaced sheet discards it. Routine/one-off editors, run preferences, review and account settings share this presenter. Recoverable errors preserve their draft state. Under the presentation policy for the same account and space, a same-scope foreground cycle keeps these drafts, review notes and navigation frozen in memory, hidden from rendering and interaction, with SwiftUI accessibility hiding applied while access is unverified. Account/access/scope loss closes protected presentation and clears it. This adds no persisted draft queue or credential storage. Creation flows register a transient completion keyed by the exact command ID, view owner and presentation epoch, distinct from the response generation that changes on backgrounding. A confirmed original or explicitly retried receipt may complete that still-owned flow once only after a current foreground response epoch passes membership and the fresh-snapshot revision floor; successful routine saves need no created ID. Editors dismiss/navigate and save-as controls record completion; failures preserve drafts. Fresh creation controls remain disabled while that view owner has an unconfirmed creation, with an explicit original-action retry available inside the editor or root menu. Explicit editor/detail abandonment, access loss, scope reset or sign-out removes callbacks; ordinary background suspension does not. The retained Routines root also preserves its pending Start owner across tab changes and unrelated checklist push/pop until one-shot receipt consumption or session/scope reset. These callbacks remain process memory, distinct from issued-request metadata. Current-source native results and the remaining hosted/device gates are recorded in Verification.

Local Supabase Auth/Postgres/HTTP integration with synthetic accounts exercises this boundary; it cannot establish hosted authorization or two-device behavior. [Backend Operations](Backend-Operations.md) describes the local and hosted workflows, and [Verification](Verification.md) records observed evidence. The [Supabase Free setup](Supabase-Free-Setup.md) has a verified private schema, two confirmed accounts and an approved live Render Free Release server with its private two-account configuration outside Git/app. Hosted pairing, shared standard commands, refresh, relaunch/foreground revalidation on both existing simulator clients, authenticated excluded-account denial, restart durability and observed Free idle/wake recovery pass against the separately recorded deployed source. This does not prove physical-device support or hosted real-media/submission review. Final local workflow and current-branch review gates remain tracked in Verification. Paid services, real media/cleanup, notifications, and distribution remain later work under the [roadmap](Roadmap.md).

The optional `SECONDLOOK_DEMO` command acceptance runner requires all three explicit UI-test/shared-test/command-check flags. It uses the installed account's Keychain-bound client. Before sending commands, it compares the vault's account, access token, refresh token, and expiry with the persisted Keychain record **inside the app process**, then forces the normal Auth refresh path; the vault must persist any rotated credentials before publishing them. No credential is returned to XCTest. Its bounded steps test accepted writes, request-bound identical retry and changed-body collision, stale space/routine versions, conflicting writes, snapshot isolation, a terminal race, closed-run denial, text-only archive, and performer self-review denial. It creates invented records without modifying pre-existing records; a final fetch checks that preservation. Reports contain only fixed step IDs and pass/fail state after a successful final refresh. Account/background changes cancel publication. The automated fixture test accepts only synthetic localhost endpoints. A separate operator-approved hosted run uses the existing stored public configuration and credentials; no token is exported and no synthetic-media route is enabled. Release excludes this runner and its hooks. Passing its checks is acceptance evidence only for the service actually contacted.

For one-member invitation recovery testing, a separate Debug hook requires `-ui-testing`, `-shared-testing`, `-shared-test-access-loss`, and both endpoints on localhost HTTP. It changes only the current vault's in-memory bearer to an invalid synthetic token. The next invitation request must be rejected by local Auth; the connected model then clears the signed-in account, protected snapshot/navigation, invitation, and Keychain session. This does not revoke an already issued token globally or simulate a hosted account change. The XCTest fixture and hook are absent from Release. See [Backend Operations](Backend-Operations.md) and [Verification](Verification.md) for the separate local scenarios and actual results.

A separate membership-recovery acceptance hook requires all explicit Debug/UI/shared flags. After genuine Auth verification, it simulates one failed membership lookup and labels that simulation on screen. Create/Join stay disabled until manual retry obtains an actual server result. The hook changes no server membership and is excluded from Release.

Dedicated localhost Debug recovery hooks can discard a decoded genuine initial-create, invitation-renewal or join response once, or enqueue concurrent saved-session restores while forcing normal Auth refresh. These hooks label the reply loss or concurrent trigger as simulated; authentication and server writes are genuine local calls. All require explicit UI/shared/scenario flags and local HTTP configuration. They expose no credentials and are excluded from Release. Additional explicit localhost probes delay publication after genuine membership fetch or simulate a decoded identity mismatch after genuine Auth refresh; those triggers are labeled simulated. The editor-denial probe uses an actual missing-reviewer command rejection. The receipt probes discard a decoded genuine command reply, then use real refresh, conditional renewal or actual Home/foreground lifecycle, and the original explicit UI retry to recover one created run. The lifecycle probe pauses publication after genuine membership lookup so protected controls can be checked before publication; reply loss and the pause are labeled simulated. Their fixture-gated tests and named synthetic-space resets belong to the local acceptance workflow.

## Future media and background work

When real media arrives, closure must write cleanup intent with the logical terminal transition; retryable workers then perform physical deletion. Private storage must grant short-lived participant reads. Notifications/reminders derive from current state after access rechecks and never become the record of truth. Uploads need stable logical IDs and unknown-outcome reconciliation. Offline intent replays only after membership/version checks. See [Product-Spec.md](Product-Spec.md) for lifecycle, privacy, and reminder contracts and [Roadmap.md](Roadmap.md) for milestone gates.

## Build and verification workflow

Open `SecondLook.xcodeproj` in Xcode or use a discovered iOS Simulator destination with `xcodebuild`; run `swift test` for the portable package and `./scripts/verify-repository.sh` for public repository safety. Exact successful commands, destinations, and limitations are recorded in [Verification.md](Verification.md). Real-device media and deletion checks require later milestones.
