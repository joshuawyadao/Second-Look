This M2 implementation has verified localhost behavior and a separate [Supabase Free setup guide](Supabase-Free-Setup.md). The hosted Supabase project/private schema and Render Free Swift command server are configured. Authenticated hosted simulator checks pass on the existing deployed source; final PR review and current-source checks remain tracked in [Verification](Verification.md). ## Structure and protocol

`Backend/` is a separately pinned Swift package. `SupabaseProvider` verifies bearer tokens through Auth and calls privileged SQL RPCs. `PrivateSpaceService` applies `SecondLookCore` commands. The initial private-space migration supplies transactional persistence; append-only `202610120001_conditional_invitation.sql` adds conditional renewal. Apply checked-in migrations in order for a new installation. The root package also exports the exact Foundation transport sources compiled by the iPhone app as `SecondLookTransport` for tests.

All wire dates use milliseconds since 1970. Successful responses are JSON with `Cache-Control: no-store`; errors expose a short code, not provider diagnostics or request bodies. A sanitized framework error handler also returns bounded JSON for missing routes and unhandled failures, without the default middleware's full-URL/error logging.

| Request | Result |
| --- | --- |
| `GET /v1/space` | Current account's `SharedSnapshot`; coded notPaired404 if not paired |
| `POST /v1/spaces`, `{}` initially or `{expectedSpaceRevision}` for renewal | `snapshot`, plaintext `inviteToken` once, `expiresAt`; renewal matches and advances the locked revision |
| `POST /v1/pairing/join`, `{inviteToken}` | Joined snapshot |
| `GET /v1/spaces/{id}` | Snapshot after membership check |
| `POST /v1/spaces/{id}/commands` | `SharedCommandEnvelope` → `SharedCommandResult` |

Initial creation requires no expected revision; renewal requires the owner's observed revision and advances it under the row lock. One concurrent renewal wins; another at the same revision receives `staleState`. The seven-argument `sl_create` owns that check/update; the six-argument compatibility wrapper can create only an absent space. Native publication of a newer revision, different space or no space clears displayed invitation metadata. Digest-only storage remains. The new migration/server contract has local acceptance; hosted source `7e32ee0` and its schema remain unchanged pending a separate operator decision.

The service accepts only the typed command envelope's top-level keys. Actor/time fields and full-state uploads are not API inputs. Space revision and domain versions are required. Explicit-space read/command and Debug synthetic-evidence responses validate that provider snapshots and receipts belong to the requested space; a wrong-space response is a bounded stored/provider failure, while unscoped discovery and pairing may identify a new space. No unpair or real evidence upload endpoint exists.

## Reproducible local checks

Prerequisites: Swift 6.2+ server toolchain (CI pins 6.2.1), Node 20+, Docker-compatible runtime, Python 3, network access to official dependency/container registries. CLI is pinned to 2.119.0. Tests use a dedicated project `secondlook-m2-local`, Docker network `secondlook_m2_local`, provider ports 56321/56322 and server port 58080. The private Unix-socket adapter in `scripts/local-docker-binding.py` forces every test container port binding to 127.0.0.1. The pinned CLI overrides Docker network binding defaults, so the launcher also verifies actual container bindings before creating accounts. It does not change the Docker daemon or user context. Do not replace these with hosted endpoints.

The adapter accepts a local Unix Docker socket only. It bounds incoming request bodies to 8 MiB and upstream response headers to 64 KiB. For Docker `POST /exec/{id}/start` and `POST /containers/{id}/attach` streams, it forwards an explicit HTTP `101` Upgrade in both directions. It also handles Docker's `200` raw or multiplexed stream response **only** on those exec/attach routes with the expected Docker stream content type. Both forms forward client stdin and upstream output concurrently, preserve a client half-close, and retain the response's original status/header bytes. A `200` from an unrelated route is ordinary HTTP, not a hijacked stream. Ordinary responses retain close/stream behavior. Fake Unix-socket regressions cover both stream status forms, stdin, framed output, half-close and ordinary HTTP without a daemon; named-container refusal and loopback rewriting remain enforced. Static error phase names avoid leaking Docker request, response, path, or credential content.

Fresh setup in the [pinned CLI's database bootstrap](https://github.com/supabase/cli/blob/v2.119.0/apps/cli/src/command-internal/db-bootstrap/db-setup.ts#L380-L429) runs an unnamed Auth migration container. The **only** unnamed-create exception requires a missing or empty `name` query value, both `com.supabase.cli.project` and `com.docker.compose.project` labels equal to `secondlook-m2-local`, and `HostConfig.NetworkMode` exactly `secondlook_m2_local`. A named create must instead use the `supabase_*_secondlook-m2-local` naming scope; matching labels alone cannot admit an unrelated named container. All admitted create requests have their published binding hosts rewritten to `127.0.0.1`. This exception does not authorize arbitrary utility jobs or change Docker-wide settings.

After fully forwarding an ordinary response, the adapter closes its write side and discards at most 64 KiB of downstream input for at most one second before closing the socket. This avoids Linux TCP resets caused by unread client input while keeping ordinary HTTP one-way. The drain never forwards that input upstream; strict socket regressions require a complete exact response and clean EOF, including a client that does not half-close.

Every recognized verifier phase has a finite deadline; a timed-out child and its owned process group receive bounded TERM/KILL and are reaped, and server shutdown remains in `finally` cleanup. Public diagnostics use fixed safe phase labels without leaking commands, credentials or private fixture content. Its default exercises legacy JWT API keys; `--modern-keys` uses the local stack's actual modern publishable/secret keys, including Auth administration without an invalid API-key bearer header. CI runs both modes. Credentials and logs live in a mode-restricted temporary directory; they are never printed or committed. Gated integration tests skip without a fixture; a skipped test is not acceptance evidence. The script must finish successfully to count local integration evidence.

Supabase's additional startup debug output also stays in that private log. If startup fails, the verifier reads at most its last 128 KiB and emits only fixed hints for Docker/API compatibility, image/registry, port conflict, health timeout, migration, database connection or CLI configuration. Ambiguous logs remain unknown but list their recognized static categories; unavailable logs and unrecognized errors are distinguished. No raw log line or credential enters CI output; a hint is not evidence of a repair. Inspect the private log locally when it is insufficient. Reusing `SECONDLOOK_BACKEND_SCRATCH` also reuses its compiler module caches to avoid rebuilding dependencies solely because a private fixture directory changed.

Adapter failures distinguish only fixed phases: project-scope refusal, malformed/bounded request, upstream connect/send, response read and downstream write. If several phases occur, the report lists their whitelisted names in first-observed order within the bounded tail, with the cause explicitly unconfirmed. It never prints container names, socket paths, headers, request data or exceptions. Socket tests use portable short temporary paths on macOS and Linux.

## Server configuration

Configure environment outside Git. Required values: `SECONDLOOK_PROVIDER_URL` (HTTPS), `SECONDLOOK_PUBLISHABLE_KEY` (public), `SECONDLOOK_SERVICE_KEY` (server only), and `SECONDLOOK_ALLOWED_ACCOUNTS` (two distinct provider UUIDs, comma-separated). `SECONDLOOK_PORT` defaults to 8080. Service startup rejects incomplete/unsafe configuration without printing its contents, including recognizable modern or legacy keys in the wrong public/service slot. Bounded decoded legacy role claims are only a configuration format check and never authenticate a key or user. Modern Supabase `sb_secret_` RPC credentials are sent on `apikey` only; legacy JWT service-role credentials retain their bearer header for localhost compatibility. Auth verification always sends the actual user's bearer token, never the server credential as user identity.

`Backend/Dockerfile` builds the server in Release using the pinned official Swift 6.2.1 image and starts it in the production environment as an unprivileged user. Build from the repository root so its dependency-free core package is available. The allowlisted `.dockerignore` excludes private runtime files and local fixtures. The Dockerfile declares no `ARG` and never references credentials. Render automatically supplies service environment variables as build arguments as well as at runtime; do not describe its environment UI as runtime-only storage, or consume sensitive arguments during the build. See the [setup guide](Supabase-Free-Setup.md) for the vendor guidance, Free-host settings and runtime configuration. Container health is process liveness, not proof of provider readiness.

For local tests only, `SECONDLOOK_LOCAL_DEVELOPMENT=1` allows a loopback HTTP provider and binds the server to 127.0.0.1. Debug additionally permits `SECONDLOOK_TEST_EVIDENCE=1` with that loopback configuration and a non-production application environment. It exposes `/_testing/synthetic-evidence`; this creates metadata labeled `M2-SYNTHETIC-NO-REAL-PHOTO` and uses normal actor/version/persistence checks. No real image is uploaded. Release and normal composition must not accept this route. Never enable it for hosted acceptance.

## Native connection

In local Settings, choose the private shared space flow and enter only public provider URL, publishable key and Swift-server URL. Sign in using an operator-created account. There is no signup or role selection in the connected flow. Either allowed account can create; the other must use the targeted invitation. The public key does not grant access to private tables/RPCs. High-priority evidence capture remains unavailable until M3; server test metadata is labeled synthetic.

Credentials use Keychain; connected snapshots are memory-only. Signing out immediately clears protected UI, navigation and the local credential. It does not promise immediate global access-token revocation: issued access tokens follow provider expiry semantics. Fresh verification and membership checks still run on server requests.

The native transport keeps Supabase Auth failure decoding separate from command-service errors. Auth HTTP 400 `invalid_credentials` becomes a bounded incorrect-email/password error; `refresh_token_not_found` and `refresh_token_already_used` require a fresh sign-in. Unknown or malformed Auth400 replies remain invalid responses, and command-service `code` mapping is unchanged. Product UI never displays raw provider messages or request contents. [Supabase's error reference](https://supabase.com/docs/guides/auth/debugging/error-codes) documents the recognized codes; synthetic transport regressions cover their wire shapes and successful sign-in/session decoding.

Debug UI acceptance uses both `-ui-testing` and `-shared-testing`, a separate Keychain namespace, simulator-only ad hoc signing with the Debug Keychain entitlement, and public configuration passed by the UI test runner. The private fixture is never bundled into the app or Release. The additional `-shared-no-periodic-poll` launch argument disables only the five-second timer for these explicit XCTest launches; foreground/background revalidation and the manual Refresh shared state action continue to work. Normal app launches retain polling.

An additional explicit `-shared-command-checks` flag runs Debug command acceptance on an already paired account. All three flags are required: `-ui-testing`, `-shared-testing`, and `-shared-command-checks`. Before commands, the installed vault compares its account ID, access token, refresh token, and expiration with the stored Keychain record inside the process, without exporting a credential to XCTest. It then forces the normal Auth refresh path; the vault saves rotated credentials to Keychain before using them. It checks request-bound retries/collisions, stale revisions, conflicting writes, immutable run snapshots, terminal races, closed-run denial, text archives, and performer self-review denial without a submission. It creates invented text records and leaves pre-existing records untouched. Its result appears only after completion and successful final refresh as fixed pass/fail step IDs; no token, snapshot, raw provider error, or request content is displayed. Background/account changes cancel the task and clear the result. Normal Debug launches and Release do not run it. For a running paired synthetic server, `verify-connected-native.py --fixture /absolute/private/ui-fixture.private.json --only-shared-commands` selects just this case. Hosted use requires the existing approved account/configuration and must omit `-reset-demo`; local fixture execution is not hosted evidence.

For an explicitly approved hosted run on an existing signed-in simulator, use `python3 scripts/verify-hosted-native.py --simulator <booted-iPhone-UDID> --public-configuration /absolute/private/public-config.json --derived-data /absolute/private/build-directory`. The JSON contains exactly `authURL`, `publishableKey` and `serverURL`; both endpoints must be hosted HTTPS and the key must be publishable. Before building, the wrapper verifies the installed Debug app's selected shared environment and exact saved public configuration. It runs only the existing-session hosted XCTest, with no password fixture or reset; every write creates invented acceptance records. Build/test have bounded deadlines, full logs remain private outside Git, and the temporary runner configuration is removed. A timeout stops only its owned process group; the identified simulator's test runner may still need separate cleanup. Ordinary test runs skip this hosted case. Actual results and deployed source are recorded separately in [Verification](Verification.md).

The same hosted wrapper with `--only-membership-recovery` selects the clearly labeled simulated lookup-failure scenario. Genuine Auth verification precedes the simulated discovery error; manual retry then reads actual server membership without creating/joining a space. Normal launches never enable this hook. Native endpoint validation requires a nonempty host, HTTPS (or explicitly allowed localhost HTTP), no embedded credentials/query/fragment and an empty/root path. Server startup additionally rejects empty keys and whitespace/control characters anywhere in either provider key and recognizable modern keys placed in the wrong public/service slot, without silently trimming them. Invalid client bodies remain HTTP400; invalid provider/stored responses become bounded HTTP503 and do not expose raw diagnostics.

For a command whose reply is lost or invalid, retry the same action to reconcile its original request-bound receipt. Matching retries may return a newer current snapshot revision with the same original created ID; they remain the same action, not a second write. Creation result IDs are checked against the returned performer-owned run/source or immediate save-as routine; repeats must name a distinct run, while a later exact save-as replay may outlive routine deletion. Noncreation results require a nil ID. Invalid result metadata leaves the original command unresolved. Five focused created-ID cases and the 117-test Core/transport package pass; connected native acceptance remains pending. The coordinator keeps that command's ID, body, space and expected revision across snapshot refreshes within the active session. A confirmed reply also leaves a session-memory receipt tied to the exact scope, command ID/body, committed revision and optional created ID until the original owner acknowledges it. Explicit retry of that confirmed ID does not send another HTTP command; one-shot consumption requires genuine membership and an active same-scope snapshot at or above the receipt revision. The coordinator retains its highest verified revision independently after consumption across same-scope background/rebind. Duplicate or delayed responses cannot restore an acknowledged receipt, and old response generations cannot complete a creation callback. A new explicit ID represents a separate intent. Background suspension hides protected state and retry controls but retains already-issued request metadata privately in memory. Verified same-scope membership and coordinator refresh restore retries; changed backend/account/space, genuine not-paired or scope-mismatch state, access loss or sign-out clear them. A command-level loss immediately invalidates model and coordinator generations, purges all issued actions and protected presentation, keeps the Auth vault only for revalidation, and cannot publish a late result. No request metadata survives process termination, and this does not add a durable offline intent queue.

The public-key field rejects recognized modern `sb_secret_` keys and legacy JWTs whose decoded role is `service_role`, including before Auth HTTP. This format check does not authenticate a public key with Supabase. Malformed successful Auth user bodies are provider failures rather than allowlist denials. Sign-out records a scoped preference barrier before checked Keychain deletion; if cleanup fails, the account remains signed out, the app reports a bounded error, and relaunch retries deletion without restoring the old record. Both unauthenticated and forbidden saved-session restoration results use that checked cleanup/barrier path; transient provider failures preserve the saved credential for a later retry. Only a successful verified new credential write removes that barrier. No credential is stored in the preference marker.
